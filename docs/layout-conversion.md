# Multilingual conversion contract

FlicKey repairs keyboard-layout mistakes; it does not translate languages or correct arbitrary spelling. Its product standard is accurate, local recovery backed by evidence, with conservative automatic edits and explicit limits.

## Evidence order

1. **Verified physical keys.** The current contiguous typing run retains at most 256 key positions and modifiers in memory. Replaying them in the source layout must reproduce the text exactly before they may be rendered in the destination layout. This distinguishes Arabic `b` from `g+h`, duplicate Armenian keys, Shift, Caps Lock, and Option without guessing from spelling.
2. **Keyboard reconstruction.** For selections, edited text, and runs without valid key history, reconstruct scalar sequences using macOS keyboard data. Preserve dead-key composition state, combining marks, punctuation, separators, and unmapped text. Offer local alternatives for ambiguous outputs, including mixed interpretations within a word.
3. **Dictionary evidence.** Manual conversion can choose a unique valid reading per word when a local dictionary supports it. Automatic detection behavior is inherited unchanged from main.
4. **Explicit manual fallback.** With no decisive word evidence, retain a deterministic physical-key reading. It is best effort: text that has lost its original key identity cannot always be recovered uniquely. Unsupported input methods and configurations with fewer than two usable layouts leave the original text unchanged.

No keystroke history is persisted, logged by the trace, or sent to a service. Mouse/caret boundaries, unaccounted-for edits, source mismatches, and failed replay validation prevent stale key history from overriding text. Candidate searches are bounded to keep conversion responsive.

User-facing correction applies compatibility rules after identifying the keys: capital-letter mistakes still recover Hebrew letters even though Hebrew's Shift plane echoes Latin; distinct Arabic shifted letters remain distinct. Currency and typographic symbols remain intact unless the captured sequence supplies evidence of letter composition. An unassigned target plane must not silently delete input. The native replay oracle tests raw layout behavior separately from these correction rules. Unambiguous manual conversions do not call the spell checker.

## Coverage and limits

The native regression matrix uses English ABC, Russian, Ukrainian, Bulgarian Standard, Greek, Hebrew PC, Arabic PC, Persian Standard, French, German, Spanish ISO, Turkish Q, Thai, Hindi InScript, Armenian HM QWERTY, and Georgian QWERTY. Expected text is generated by an independent direct `UCKeyTranslate` oracle. Four modifier scenarios across every distinct source/target pair produce 960 assertions.

Targeted regressions cover Arabic `bright` and `bad night`, Greek/Spanish accents, Thai combining marks, Hindi virama, Russian shifted punctuation, Unicode normalization, emoji, whitespace, stale traces, unsupported IMEs, ambiguous source scores, and bounded searches.

Compatibility QA also compares the previous converter with 60,624 English/Hebrew/Russian cases. All 30,000 sampled base-key runs match, as do English/Hebrew capital runs; remaining differences are intended Russian shifted-punctuation and accent recovery. These fixed samples are regression evidence, not universal accuracy estimates.

The original 480-phrase diagnostic improved from 349 to 447 exact matches using text-only conversion without dictionary assistance. This is a fixed diagnostic sample, not an estimate of user-wide accuracy. The remaining cases include irreversible duplicate-key ambiguity, case-policy ambiguity, and unfinished source composition. Exact key replay passes all 960 tested cases; this does not certify all possible key sequences or every editor.

Automatic word validation still depends on functional macOS dictionaries. On the audited host, English, Russian, Hebrew, French, German, Spanish, and Turkish passed the app's dictionary probe; Arabic, Greek, Ukrainian, Bulgarian, Persian, Thai, Hindi, Armenian, and Georgian did not. Installing a keyboard layout is not proof that its spell checker works.

Chinese/Japanese/Korean composition input methods are not covered by the static keyboard-layout mechanism. Do not advertise universal IME support. Live field replacement, event delivery, third-party input methods, keyboard hardware variants, and text-service changes require separate integration QA.

The isolated multilingual-only snapshot is based on `main` at `4d1f6ff`. All 559 host unit tests pass, including the native 16-layout recovery matrix. It includes the existing automatic-switch behavior from main unchanged; the newer continuous-typing changes are excluded. The combined branch also passed 12 focused VM UI tests, but those UI results are not attributed to this isolated snapshot.

## Regression commands

- `xcodebuild test -scheme FlicKey`: all host unit tests, including native-layout checks.
- `scripts/tart.sh fix-ui`: live manual conversion, uppercase/mixed-case recovery, toggle-back, and custom shortcut persistence.
- `scripts/tart.sh spotlight-ui`: replacement in Spotlight's search field.

The strengthened product brief is: **Build the most trustworthy offline keyboard-layout recovery tool possible: use verified key evidence before inference, preserve Unicode and composition, make automatic edits only with decisive evidence, leave unsupported inputs intact, remain responsive, and prove each support claim with reproducible native-layout and editor-level tests.**
